## 🎯 Executive Summary & Business Problem

Customer churn directly impacts growth and valuation — acquiring a new customer costs **5–7x more** than retaining an existing one. In production environments, standard churn models often fail due to subtle **data leakage** (evaluating features on the same observation timeframe as the churn definition) and synthetic dataset over-separation.

This project implements an industry-grade, **leakage-free** customer analytics and retention system:
1. **Relational Data Warehouse:** Multi-table customer, order, and omnichannel interaction model (10,500+ records) with log-normal order sizing and realistic behavioral noise.
2. **Advanced SQL Analytics:** 7 production-grade SQL queries utilizing Common Table Expressions (CTEs), window functions (`RANK`, `LAG`, `SUM OVER`), correlated subqueries, and `JULIANDAY` date arithmetic.
3. **Observation-Performance Window Architecture:** Strict temporal split ensuring zero feature lookahead or target contamination.
4. **Machine Learning Pipeline:** Tuned ensemble classifiers (`LogisticRegression`, `RandomForestClassifier` with 5-fold `GridSearchCV`, and `GradientBoostingClassifier`) wrapped in `Pipeline` objects to eliminate cross-validation scaler leakage.
5. **Business Impact & Strategy:** Quantitative RFM segmentation identifying **171 high-risk customers** and **$135,931 revenue at risk** with prioritized ROI-driven intervention playbooks.

## 🛡️ Production ML Methodology: Eliminating Data Leakage

Many portfolio churn projects artificially report `>0.98 ROC-AUC` due to design flaws:

| Flaw in Naive Churn Pipelines | How This Project Solves It |
|---|---|
| **Label-Feature Collinearity:** Defining churn as `recency > 90` while including `recency` as an input feature. | **Independent Ground Truth:** Target `churn_flag` is assigned independently with a ~15% noise rate, forcing models to learn true behavioral engagement rather than memorizing a threshold rule. |
| **Temporal Data Leakage:** Calculating features using transactions from the entire timeline, including the churn evaluation window. | **Observation-Performance Window Split:** Features are calculated strictly from the **Observation Window** (tenure up to `2025-04-01`). The **Performance Window** (`2025-04-01` to `2025-06-30`) is reserved exclusively for target evaluation. |
| **Preprocessing Leakage in CV:** Scaling the entire dataset (`fit_transform`) before running cross-validation. | **Scikit-Learn Pipelines:** All models wrap `StandardScaler` inside a `Pipeline()`, guaranteeing test folds remain unseen during fitting. |
| **Over-reliance on ROC-AUC:** Using ROC-AUC alone on an imbalanced dataset (29% churn rate), masking poor minority-class precision. | **Dual ROC & PR-AUC Evaluation:** Evaluating both ROC-AUC and Precision-Recall AUC (`average_precision_score`) to optimize for precision and recall on actual churners. |

```
│                (Customer Signup → 2025-04-01)               │   (2025-04-01 → 2025-06-30)  │
```

## 📊 SQL Analytics Suite (SQLite Warehouse)

The database schema and analytical queries are executed via `scripts/sql_analysis.py` and exported to `outputs/SQL_Analysis_Results.xlsx`:

### Query Capabilities Demonstrated:
- **CTE & Month-over-Month Growth with `LAG()`:** Computes monthly completed order revenues and MoM growth trajectories.
- **Window Functions for Cumulative Contribution (`SUM OVER`, `RANK`):** Partitions customers across country cohorts and calculates running revenue percentiles.
- **Correlated Subqueries:** Computes top product categories per geographic market dynamically.
- **Conditional Segmentation (`CASE WHEN`):** Classifies spending tiers and tenure dormancy.
- **Date Arithmetic (`JULIANDAY`):** Cohort analysis tracking days elapsed between order milestones.

```sql
-- Query 6: Monthly Revenue Trends (CTE + LAG Window Function)
WITH monthly_revenue AS (
    SELECT
        SUBSTR(order_date, 1, 7)     AS order_month,
        COUNT(order_id)              AS num_orders,
        ROUND(SUM(order_amount), 2)  AS monthly_revenue,
        COUNT(DISTINCT customer_id)  AS unique_customers
    FROM orders
    WHERE order_status = 'Completed'
    GROUP BY order_month
)
SELECT
    order_month,
    num_orders,
    monthly_revenue,
    unique_customers,
    ROUND(monthly_revenue / unique_customers, 2) AS revenue_per_customer,
    ROUND(
        (monthly_revenue - LAG(monthly_revenue) OVER (ORDER BY order_month))
        / LAG(monthly_revenue) OVER (ORDER BY order_month) * 100, 2
    ) AS mom_growth_pct
FROM monthly_revenue
ORDER BY order_month;
```

